## 三、技术选型

### 最终确定

| 层次 | 选型 | 理由 |
|------|------|------|
| 主力语言 | Java 17+ | JD覆盖面最广，参考项目生态最成熟 |
| 后端框架 | Spring Boot 3.x | 单体起步，后续可拆微服务 |
| ORM | MyBatis-Plus | 国内大厂主流，SQL可控 |
| 数据库 | MySQL 8.x | 所有JD都要求 |
| 缓存 | Redis + Redisson | 库存预热/原子扣减/限流/分布式锁 |
| 消息队列 | RabbitMQ | 参考项目主流，延迟队列支持 |
| 前端 | React + TypeScript | JD要求，用户选定 |
| 部署 | Docker + Docker-Compose | 对应电信/云原生要求 |
| 监控 | Prometheus + Grafana | 对应可观测性要求 |
| 压测 | JMeter | 参考项目通用 |

### 架构策略

单体起步 → 模块清晰拆分（用户/订单/票务分包）→ 后续按需拆微服务。面试时可以讲"单体→微服务演进"的设计思路。

## 四、数据库设计

### ER 关系

```
user (1) ──→ (N) order (N) ──→ (1) show_session (N) ──→ (1) show
                         │
                         └── (N) ──→ (1) ticket_category
```

### 6 张核心表

| 表名 | 说明 | 核心字段 |
|------|------|---------|
| `user` | 用户/管理员 | username, password, role(0=用户,1=管理员) |
| `show` | 演出 | title, venue, sale_start |
| `show_session` | 场次 | show_id, start_time（一场演出多个场次） |
| `ticket_category` | 票价档次 | session_id, price, total_stock, **remain_stock** |
| `order` | 订单 | order_no, user_id, category_id, quantity, status |
| `inventory_log` | 库存流水（审计） | category_id, change_type, quantity |

### 库存扣减流程（防超卖三重保障）

```
第一道：Redis Lua 原子扣减     ← 扛住高并发，快速过滤无效请求
第二道：SQL remain_stock > 0   ← 乐观锁兜底
第三道：回滚机制               ← 超时未支付自动归还库存
```

## 六、抢票核心流程

一次完整的抢票请求路径：

```
前端 POST /api/ticket/buy
  │
  ▼
① 限流检查（Redis令牌桶）→ 超过频率直接拒绝
  │
  ▼
② 售罄检查（Redis内存标记）→ 已售罄直接返回
  │
  ▼
③ Redis Lua原子扣库存 → 库存不足返回失败，标记售罄
  │
  ▼
④ MQ发送下单消息 → 立即返回"订单处理中"
  │
  ▼
⑤ MQ消费者取走消息 → 异步创建订单（MySQL）
  │
  ▼
⑥ 订单待支付 → 30分钟超时 → MQ延迟消息 → 取消+回滚库存
  │
  ▼
前端轮询 GET /api/order/status?orderNo=xxx
```

**为什么这样设计？**

- 限流和 Redis 扣库存是纯内存操作，抗住高并发
- MQ 做缓冲，不让 MySQL 直接被冲垮
- 前端先拿到"处理中"，轮询查结果，体验上不会卡死

## 七、关键设计决策

| 决策 | 方案 | 不做另一个的理由 |
|------|------|----------------|
| 单体还是微服务 | 单体起步，后续拆 | 上来就微服务增加分布式事务等复杂度 |
| 接口还是抽象类 | 直接用 @Service 类 | 项目规模不需要 interface+impl 分离 |
| 分布式锁用 SETNX 还是 Redisson | Redisson | 自动续期+可重入，避免死锁 |
| 延迟队列自己写还是用 MQ | RabbitMQ 死信队列 | 不需要额外组件，MQ 自带 |
| 前端选 React 还是 Vue | React | 用户选定 |
| C++ 在哪里体现 | 项目二自研网关 | 不影响主项目进度 |
